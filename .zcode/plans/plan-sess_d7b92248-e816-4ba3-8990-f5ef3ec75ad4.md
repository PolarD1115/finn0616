# 情绪/欲望状态长期不变化 — 修复计划

## 已确认根因（3 条，均已验证）

### 根因 A：网页聊天未接入情绪事件链路
- `gateway.py` 的两条网页路径都没有调用 `desire_bridge.record_user_message()` / `record_assistant_message()`：
  - 普通流式 `_handle_chat`（结束于 1543 行，之后只有双写 1553）
  - 工具循环 `_handle_chat_with_tool_loop`（结束于 1929，之后只有双写 1933）
- 仅 `heartbeat.py:725-726`（TG）和 `napcat.py:378-379`（QQ）调用了。
- 后果：网页聊天从不产生 `msg_user`/`msg_assistant` 事件 → 分类器从未被触发 → `_recent_labels` 停在旧值 `["neutral","playful","playful"]`、`last_interaction_at` 不更新（只有 TG/QQ 消息更新它）。即使数据库有 `Web_Chat` 聊天记录，情感引擎也感知不到。

### 根因 B：前端情绪字段与后端真实字段不一致
- 后端 `emotion_engine.build_display()` 产出的 16 维字段（`DIMS` 键，emotion_engine.py:48-64）：
  `vitality, longing, intimacy, possessiveness, lust, jealousy, anxiety, protectiveness, contentment, elation, seeking, play, dejection, irritability, fear` + `fatigue`
- 前端 `console.html:805,810` 和 `miniapp.html:879,884` 用的 `emoKeys` 是旧字段：
  `joy, calm, anxiety, sadness, anger, tenderness, excitement, longing, guilt, pride, shame, envy, hope, fear, disgust, surprise, fatigue`
- 二者仅 `anxiety/longing/fear/fatigue` 4 个重合，其余 12 维前端查不到值 → 永远走 `dimRow(...,"—",0,"gray")` 分支显示"—"。这就是"情绪维度进度条长期不变化"的直接原因。
- 驱动条 `_D`/`dKeys`（attachment/curiosity/reflection/duty/social/libido/stress/fatigue）字段正确，无需改。

### 根因 C：attachment=0.45 / duty=0.05 是固定基线（非 bug）
- `attachment=0.45` = `BASELINE_CAP`（desire_engine.py:150），attachment 地板漂移的硬上限，`drift_baseline()` 第 668 行 clamp 到 `[0.30, 0.45]`。观测到长期 0.45 说明漂移开关开启后地板被 cap 托住——这是设计规则。
- `duty=0.05` = `BASELINE["duty"]`（desire_engine.py:62），`map_from_emotions()` 第 320-321 行：`has_pending_task=False` 时无条件强制置为此基线，且 `pick_intent` 把 duty 排除出候选。
- **结论**：二者是固定基线设计，本次不修改业务规则参数。

```python
async def _record_desire_events(self, user_msg, channel="Web"):
    """网页聊天：用户消息分类 + AI 回复事件入队（吞异常，不影响聊天）。
    顺序：先 record_user_message（分类+msg_user），再 record_assistant_message，
    保证事件队列里 msg_user 在 msg_assistant 之前（与 TG/QQ 一致）。"""
    try:
        import desire_bridge
        await desire_bridge.record_user_message(user_msg, channel=channel)
        await desire_bridge.record_assistant_message()
    except Exception as e:
        _log(f"💗 [欲望驱动] Web 事件入队跳过：{e}")
```

## 已知风险
- **重复入队**：每次 `/v1/chat/completions` 是独立请求，`_record_desire_events` 每次只调一次，`enqueue_event` 用时间戳+随机数生成唯一 event_id，天然不重复。
- **流式结束路径遗漏**：普通流式（1543）+ 工具循环（1929）两条正常结束路径已覆盖；工具循环的 3 个失败 return 不入队（正确）。
- **分类器延迟**：`record_user_message` 内部用 `asyncio.to_thread` 调 LLM 分类，不阻塞事件循环；且在流式结束后触发，不影响首字。分类失败降级 neutral，不影响聊天。
- **前端兼容**：旧字段在前端无其他引用（仅 emoKeys 一处），改名安全；后端字段不动。
- **数据库并发**：事件队列入队是 read-modify-write（load→append→save），高并发下理论有竞态，但网页/TG/QQ 均为低频消息，心跳 tick 周期消费，实际无冲突风险（与 TG/QQ 既有行为一致）。
