# 网关 Prompt Cache 命中率修复计划

## 诊断结论

你的 cached 不稳定（4-5% 到 60-70% 波动）有 **4 个根因**，按影响排序：

### 根因 1（最致命）：`stable_system` 前缀每轮都在变
`_inject_context`（gateway.py:1416）把 `persona + user_prof + core_summaries` 当"稳定前缀"，但：
- `core_summaries`（1451 行）：每次请求都 `SELECT ... ORDER BY created_at DESC LIMIT 3`——一旦 Core_Cognition 新增/更新一条，拼接结果就变。
- `user_prof`（1462 行）：每次请求都查 `user_facts`——某个 key 的 value 被更新，或新增/删除一条导致 `rows[:60]` 集合变化，前缀就变。
- **上游 prompt cache 是严格前缀匹配**，前缀任何一个 token 变了，后面全部无法命中。

### 根因 2：DB 历史注入破坏前缀连续性
`history_msgs`（1486-1506）每轮从 DB 拉最近 10 条，插入 system 和 user 之间。每轮对话后 DB 新增一条、窗口滚动——**history 内容每轮都在移位**，而不是像客户端自带历史那样自然增长。前缀里的 history 一变，缓存全失效。

### 根因 3：Claude（中转站）没有 `cache_control` 标记
DeepSeek/Kimi/GLM 都是**自动前缀缓存**，无需参数。但 Claude 需要**手动**在消息上打 `cache_control: {"type": "ephemeral"}` 标记，不打就完全不缓存。

### 根因 4：网关侧无缓存可观测性
流式路径没设 `stream_options: {include_usage: true}`，也不解析 usage 里的缓存字段。无法看到每次请求的命中情况，只能靠上游控制台被动看。

---

## 修复方案（4 个改动，按优先级排序）

### 改动 1：TTL 缓存 stable_system 组件（最高优先级，根因 1）

**目标**：让 `core_summaries` 和 `user_prof` 在一个时间窗口内（默认 5 分钟）保持字节不变。

**做法**：
- 在 gateway.py 模块级新增带 TTL 的缓存结构，缓存 `core_summaries` 和 `user_prof` 的拼接结果。
- `_inject_context` 里查这两个值时，先查缓存命中就直接用，过期才重新查 DB。
- 新增环境变量 `STABLE_PREFIX_TTL`（默认 `300` 秒）。
- `core_summaries` 的 TTL 可独立设为更长（如 600s），因为它变化更慢（只在总结/日记生成时变）。

**预期效果**：5 分钟内的连续对话，stable_system 字节一致 → 前缀稳定 → 命中率大幅提升。

### 改动 2：缓存命中可观测性（配合改动 1 验证效果，根因 4）

**目标**：在网关侧能看到每次请求的缓存命中 token 数。

**做法**：
- 流式路径：转发前给 `req_data` 加 `stream_options: {"include_usage": true}`（DeepSeek/OpenAI 支持；Kimi/GLM 不支持会自动忽略，不报错）。
- 流式收集循环（1320-1408）：解析每个 SSE chunk 的 `dj.get("usage")`，保存最后一个（usage 通常在 finish chunk 里）。
- tool_loop 路径（1628+）：非流式响应，直接从 response JSON 取 `usage`。
- 流结束后打日志：`prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`cached_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`，以及 stable_system 的 hash（便于发现前缀何时变化）。
- 日志格式参考 Haven-Ombre 的 `_log_cache_usage`。

### 改动 3：自适应 DB 历史注入（根因 2）

**目标**：客户端自带历史时不注入 DB 历史，保留自然增长的前缀模式。

**做法**：
- `_inject_context` 开头检测：`messages` 里非 system 消息 >1 条 → 客户端已提供历史 → 跳过 DB history 拉取和注入。
- 只有 1 条 user 消息时（如管理后台测试、或极简客户端）→ 仍注入 DB 历史（缓存效果差但功能正常）。
- 新增环境变量 `INJECT_DB_HISTORY`（默认 `auto`）：`auto`=自适应、`always`=总是注入、`never`=从不注入。

**预期效果**：使用带历史的前端（主流聊天 UI）时，前缀自然增长 → 每轮命中上一轮的缓存。

### 改动 4：Claude cache_control 标记（可选，根因 3）

**目标**：使用 Claude（中转站）时主动触发缓存。

**做法**：
- 检测 `req_data["model"]` 含 `claude` 且环境变量 `CLAUDE_CACHE_CONTROL` 启用时：
  - 把 system 消息的 `content` 从字符串转为 content-block 数组格式，末尾块加 `cache_control: {"type": "ephemeral"}`。
  - 如有 tools 定义，在最后一个 tool 的描述块上也加标记。
- 默认关闭（`auto`：仅 model 含 claude 时启用；`false`：强制关）。
- **注意**：此功能依赖中转站是否支持透传 `cache_control` 字段。部分中转站会剥离未知字段导致无效，需实测验证。

---

## 改动范围

仅修改 **gateway.py** 一个文件，不新增文件、不改数据库 schema、不影响其他模块。

## 实施顺序建议

1. **先做改动 1 + 2**（TTL 缓存 + 可观测性）→ 部署后观察日志中的命中率变化。
2. 确认改动 1 生效后，**再做改动 3**（自适应历史注入）。
3. **改动 4** 按需启用（仅用 Claude 时）。

## 风险评估

- **改动 1**：极低风险。最坏情况是 5 分钟内看到稍旧的画像/总结，但这对聊天体验影响极小。
- **改动 2**：极低风险。仅加 `stream_options` 和日志，不改业务逻辑。
- **改动 3**：中低风险。改变了历史注入行为——如果客户端发历史但格式不规范（如全是 user 消息），可能影响上下文质量。通过 `INJECT_DB_HISTORY=always` 可回退。
- **改动 4**：低风险（opt-in）。最坏情况是中转站不认 `cache_control`，静默无效。
